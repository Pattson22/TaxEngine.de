# TaxEngine.de

Consumer FinTech SaaS: German tax residents enter income/deductions for
free, get an estimated refund, and pay a flat €34.90 processing fee to
electronically submit their return to the Finanzamt via ELSTER. Operates
purely as tax-preparation software (no advisory service), staying inside
the Steuerberatungsgesetz software safe-harbor.

## Setup

```bash
# 1. Backend dependencies
cd backend
python -m venv .venv && .venv\Scripts\activate   # Windows
pip install -r requirements.txt

# 2. Configure
cp .env.example .env   # edit DATABASE_URL / JWT_SECRET_KEY to match your setup

# 3. Database -- create an empty Postgres database, then:
alembic upgrade head

# 4. Run the API
uvicorn app.main:app --reload
# -> interactive API docs at http://localhost:8000/docs
```

### Migrations

`db/schema.sql` is a frozen historical snapshot only (see its header) --
Alembic is authoritative going forward:

```bash
alembic upgrade head                              # apply all pending migrations
alembic revision --autogenerate -m "add X"         # generate a new migration from model changes
alembic downgrade -1                               # roll back one migration
```

`alembic/env.py` pulls the connection string from `app.config.settings`
(i.e. `DATABASE_URL`/`.env`), not from `alembic.ini`, so there is exactly
one place the DB URL is configured. `create_type=False` on every enum
column in `app/models/enums.py` is what stops `Base.metadata` (used
implicitly by `--autogenerate`) from trying to redundantly manage type
lifecycle outside of migrations — Postgres ENUM `CREATE TYPE`/`DROP TYPE`
is handled explicitly in the migration file itself (autogenerate does emit
`CREATE TYPE` automatically for a brand-new table/column, but does NOT
emit the matching `DROP TYPE` on downgrade — that gap was caught while
verifying the initial migration's downgrade path and is now handled by
hand in `alembic/versions/..._initial_schema.py`).

### API surface (v0)

| Route | Purpose |
|---|---|
| `POST /auth/register`, `POST /auth/login` | Account creation, JWT session token |
| `GET /users/me`, `PATCH /users/me` | Profile (tax class, church tax, joint assessment, ...) |
| `POST/GET /wage-tax-certificates`, `GET/DELETE .../{id}` | Lohnsteuerbescheinigung data |
| `POST/GET /deductions`, `GET/DELETE .../{id}` | Werbungskosten/Sonderausgaben/credit line items |
| `POST/GET /tax-filings`, `GET .../{id}` | Per-year filing record |
| `POST /tax-filings/{id}/calculate` | Runs the full `tax_engine` pipeline, persists the refund breakdown |
| `POST /tax-filings/{id}/pay` | Marks the flat fee paid (placeholder — not wired to a real payment provider yet) |

`POST /tax-filings/{id}/calculate` is the integration point worth reading
first: `app/services/tax_calculation_service.py` loads a user's wage
certificates and deductions for a tax year, dispatches each deduction
category to the matching `tax_engine` function (or trusts
`amount_claimed_cents` for categories with no dedicated algorithm yet),
and writes the resulting income tax / Soli / church tax / refund estimate
back onto the `tax_filings` row.

## Financial Data Integrity Principles

These are non-negotiable across the codebase:

- **Integer cents, never float, for any money value** — in the DB
  (`BIGINT ... _cents` columns) and in Python (`int`, or `Decimal` only
  where legally-mandated formulas require intermediate fractional
  precision, as in `tax_brackets.py`).
- **Every legal constant lives in one place** (`tax_engine/constants.py`),
  versioned per tax year, never inlined — an annual bracket/rate update is
  a one-file, reviewable diff.
- **Computed deductions are recomputed from structured inputs**, not
  trusted as client-submitted totals — `deductions.details` (JSONB) stores
  `distance_km`/`days_worked`/etc., and the engine derives the amount. The
  `DeductionCreate` Pydantic schema validates that payload against the
  category's expected shape at WRITE time (a malformed request 422s
  immediately), not just when a filing is calculated.
- **`tax_engine/` has zero web/DB imports** — it is a pure calculation
  library, independently unit-testable and reviewable in isolation.
  `app/services/tax_calculation_service.py` is the one place DB rows and
  `tax_engine` inputs/outputs meet.
- **Alembic migrations are the authoritative schema source**, not
  `Base.metadata.create_all()` and not `db/schema.sql` (now a frozen
  reference) — every SQLAlchemy model declares its CHECK constraints and
  indexes via `__table_args__` specifically so `alembic revision
  --autogenerate` produces an accurate diff; the `updated_at` trigger is
  the one piece with no SQLAlchemy representation and is added by hand in
  the migration file.
- **The §32a bracket calculation is an explicitly-labeled placeholder** —
  the only value transmitted to the Finanzamt must come from the certified
  ERiC library (see `docs/ELSTER_ERIC_INTEGRATION.md`), not from this
  scaffold's approximation.

## Verification

- `backend/tests/` — 121 pytest unit tests, 100% line coverage of
  `tax_engine`, run with `python -m pytest`.
- The full HTTP stack (routes -> models -> `tax_calculation_service` ->
  `tax_engine` -> Postgres) was smoke-tested end-to-end against a real,
  throwaway Dockerized Postgres instance: register/login, auth rejection
  paths, wage certificate + all four computed deduction categories,
  write-time validation rejecting a malformed deduction payload, filing
  creation/duplicate-rejection, `/calculate`, and `/pay`. The calculated
  figures were cross-checked against an independently hand-verified
  worked example and matched exactly.
- The Alembic initial migration was verified against `db/schema.sql` by
  applying each to a separate throwaway Postgres container and diffing
  `pg_dump --schema-only` output — confirmed byte-for-byte equivalent
  (modulo incidental whitespace inside one function body). A full
  `upgrade head` -> `downgrade base` -> `upgrade head` cycle was also run;
  the first attempt at this caught a real bug (Postgres ENUM types aren't
  dropped automatically when their table is dropped, so a second upgrade
  failed with "type already exists") which is now fixed with explicit
  `DROP TYPE` statements in the migration's `downgrade()`.

## Status

Foundational MVP: schema + calculation engine (employee income, Grundtarif
and Splittingtarif, Soli, Kirchensteuer, commute/home-office/donations/
childcare deductions, the §35a Handwerkerleistungen credit) + a working
FastAPI + SQLAlchemy API layer wired end-to-end to that engine + Alembic
migrations + the ELSTER integration design. See `docs/TAXFIX_GAP_ANALYSIS.md`
for a feature-by-feature comparison against Taxfix and the prioritized
roadmap of what's still missing (capital gains, rental income,
self-employment income, Kinderfreibetrag/Kindergeld Günstigerprüfung, live
ERiC integration).

Not yet implemented: real payment-provider webhook verification, the
actual ERiC worker service, and the frontend.
